## Context

The Agent dialog currently edits `command` and flattens a whitespace-separated Args input into `args[]`. Claude Code, Codex, Antigravity CLI, and GitHub Copilot CLI expose overlapping concepts with different flags and accepted values. Their installed versions and available models vary by machine, account, and model gateway, but the application must not execute or inspect a user's CLI installation at runtime.

The implementation evidence and exact locally observed CLI outputs are recorded in [`docs/ideas/2026-10-06-agent-cli-command-builder-research.md`](../../../docs/ideas/2026-10-06-agent-cli-command-builder-research.md). That file remains a research note for maintainers, not a runtime trust source.

The dispatcher already owns prompt delivery (`-p`, `--print`, `--prompt`, Codex `exec`, etc.), worktree selection, and lifecycle control. A command builder must therefore configure only the user-owned launch options and must not duplicate dispatcher-owned arguments.

The runtime is intentionally catalog-driven. It reads a checked-in JSON capability file generated by a maintainer-only script, and that catalog defines the static system-of-record for supported fields and discoverable model suggestions.

## Goals / Non-Goals

**Goals:**

- Make common Agent launch options selectable without requiring users to memorize CLI syntax.
- Keep a reviewed, deterministic capability catalog for the supported CLIs in the repository.
- Preserve existing and future arguments that the builder does not recognize.
- Keep the resulting `agents.yaml` compatible with current readers and runners.
- Ensure the runtime never monitors or executes a user environment's installed agent CLIs.

**Non-Goals:**

- Managing CLI authentication, subscriptions, or provider credentials.
- Treating the bundled model list as an authorization or entitlement guarantee.
- Replacing each CLI's interactive model picker.
- Moving prompt, worktree, or subprocess routing responsibilities from `AgentRegistry`/`AgentRunner` into the UI.
- Supporting arbitrary executable discovery supplied by a remote client.

## Decisions

### 1. Maintain a checked-in generated catalog instead of runtime probing

The repository includes a generated JSON file, `server/agent-cli-capabilities.json`, plus a maintainer-only generator script at `scripts/generate-agent-cli-capabilities.ts`. The catalog contains the canonical alias list, observed source version, supported structured fields, category/kind/choice metadata, danger flags, model guidance, and any models discoverable on the development machine.

The runtime is never permitted to spawn `claude`, `codex`, `agy`, `copilot`, `app-server`, or model-list commands. A request may select only a known adapter and only read the bundled file; it cannot supply a probe command line.

Alternative considered: probe the user's machine on demand and cache the results. Rejected because the architecture requirement explicitly forbids runtime CLI execution or inspection in the user environment.

### 2. Keep the catalog generator explicit and maintainable

Maintainers run the generator through the explicit `npm run generate:cli-catalog` command. The npm script passes the generator's required `--write` opt-in on every platform; importing or invoking the generator without that flag refuses to probe. The script is allow-listed and only executes the supported installed CLIs for a developer snapshot. The generated JSON is deterministic and reviewable in git history.

This keeps the runtime safe while still permitting a set of curated, versioned capability snapshots that can be reviewed before release.

The catalog generator and the real-CLI argv smoke test are separate operations. `npm run generate:cli-catalog` refreshes the reviewed snapshot. `npm run test:cli-argv` starts only allow-listed installed CLIs with catalog-derived arguments, supplies no prompt, recognizes parser rejection output, and terminates accepted long-running invocations after a bounded grace period. `npm run test:cli-argv:all` additionally requires every supported CLI to be installed.

The real-CLI smoke test remains an explicit maintainer action and is not part of GitHub Actions. CI uses deterministic fixtures only, because hosted runners neither install nor authenticate every supported agent CLI. This also prevents a repository test from unexpectedly contacting a model provider. No prompt is submitted by the maintainer smoke test, so it performs no model inference, although an individual CLI may still initialize its local configuration, check authentication, or inspect resumable sessions.

### 3. Keep `command` and `args[]` as the persistence contract

The UI parses recognized arguments from the existing `args[]`, edits those values structurally, and writes the merged argv back through the existing Agent config endpoint. Manager session lifecycle is stored separately in the optional `sessionStartup` field.

Unknown arguments remain ordered and are editable in a dedicated free-form args field. Saving without editing them preserves them byte-for-byte as array elements. Conflicting duplicate recognized flags are surfaced to the user instead of silently discarded.

Alternative considered: persist a second structured builder object. This is rejected because it creates two sources of truth and would require migrations in every consumer.

### 4. Separate user-owned launch options from dispatcher-owned prompt arguments

The builder SHALL NOT add `-p`/`--print`, Codex `exec` prompt content, change IDs, artifact contracts, or other runtime prompt transport. Those remain resolved by `AgentRegistry` and `AgentRunner`.

### 5. Provide a staged UI with deterministic category grouping

The Agent dialog keeps Command selection first. Once the command maps to a supported adapter, the UI presents fields described in the catalog using the canonical ordered groups Model, Reasoning, Permissions, Sandbox, Execution, Context, Tools & Access, and Unattended / Dangerous. Model and Reasoning sections open by default; the remaining normal categories are collapsed until the user expands them, and empty categories are omitted entirely. Dangerous or unattended flags remain in their own warning-colored section instead of being mixed into permissions or sandbox controls.

The UI uses native `<details>/<summary>` sections with an explicit disclosure indicator for keyboard-accessible expansion. A dedicated free-form args editor remains visible independently of those groups. The UI omits a redundant read-only Advanced preview; an unknown command continues to use the existing manual Args editor and is never blocked by the builder.

## Risks / Trade-offs

- **Catalog drift** → Keep the generator and the JSON under version control and add drift tests that compare the catalog against the static adapter metadata used by the web and server.
- **Account-specific model availability** → Treat catalog models as suggestions, not authorization. The model field stays editable so users can override or enter a different value when required by their account or provider.
- **Builder overwrites an option it does not understand** → Round-trip unknown argv tokens and test mixed recognized/unrecognized sequences.
- **Quoted values cannot be represented by a naive whitespace split** → Use the argv-aware free-form editor and parser rather than splitting on whitespace at save time.
- **Dangerous approval options become too easy to enable** → Label their impact, require an explicit selection, and do not enable them by default.
- **Windows executable names and process behavior differ** → Resolve adapter aliases independently from the executable path and test `.exe`/`.cmd` compatibility in the static catalog and parser logic.

## Migration Plan

1. Add the checked-in catalog and the maintainer-only generator without changing Agent persistence.
2. Keep the parser/serializer and category logic fully deterministic in the server and web code.
3. Replace the primary runtime probe path with catalog-backed lookup while keeping the free-form args fallback intact.
4. Verify existing `agents.yaml` files reopen and save without argument drift.
5. Roll back by removing the catalog entry or by regenerating it; the stored schema remains the same because persistence is unchanged.

## Open Questions

- Whether future maintenance snapshots add new adapters or additional model entries for the same CLI; the catalog schema supports those updates without changing the persisted `command` + `args[]` contract.
