# Agent CLI command builder

This UI uses a checked-in capability catalog rather than probing the user's environment at runtime. The catalog is generated by maintainers with an explicit opt-in script and is committed to the repo so the app remains safe and deterministic.

See the source research note at [docs/ideas/2026-10-06-agent-cli-command-builder-research.md](../ideas/2026-10-06-agent-cli-command-builder-research.md) for the original discovery notes and version-dependent caveats.

## Why the runtime does not inspect local CLIs

The architecture explicitly forbids runtime execution or inspection of user-installed Claude Code, Codex, Antigravity, or GitHub Copilot CLIs. The application does not resolve executable paths, spawn `app-server`, or call model-list commands while the dashboard is open. This avoids user-environment scanning and prevents arbitrary subprocess execution from the UI or server runtime.

Instead, the project ships a generated file at `server/agent-cli-capabilities.json`. The runtime reads that static catalog and treats it as the system-of-record for supported fields and model suggestions.

## Maintainer workflow

Maintainers regenerate the catalog intentionally:

```bash
ITHYNO_GENERATE_CLI_CATALOG=1 npm run generate:cli-catalog
```

The script is allow-listed and only probes the supported CLIs when the maintainer explicitly runs it. The checked-in JSON is then reviewed and shipped with the app.

## Supported field behavior

The builder renders the fields defined in the bundled catalog. These are grouped in a deterministic order that matches the runtime contract:

1. Model (`--model`, `--profile`, `--auto-tier`)
2. Reasoning (`--effort`, `--reasoning-effort`)
3. Permissions (`--permission-mode`, `--ask-for-approval`, `--approve-for-me`)
4. Sandbox (`--sandbox`)
5. Execution (`--mode`, `--autopilot`, `--plan`)
6. Context (`--context`, `--add-dir`)
7. Tools & Access (`--allow-tool`, `--deny-tool`, `--allow-url`, and equivalent adapter-defined access controls)
8. Unattended / Dangerous (warning-colored, explicit opt-in only)
9. Advanced (unrecognized argv editor, always last)

- Claude Code: `--model`, `--effort`, `--permission-mode`, `--dangerously-skip-permissions`
- Codex: `--model`, `--profile`, `--sandbox`, `--ask-for-approval`, `--approve-for-me`, `--dangerously-bypass-approvals-and-sandbox`
- Antigravity (`agy`): `--model`, `--effort`, `--mode`, `--sandbox`, `--dangerously-skip-permissions`
- GitHub Copilot CLI: `--model`, `--reasoning-effort`, `--context`, `--auto-tier`, `--mode`, `--allow-all`, `--yolo`

Dangerous controls remain visible but are labeled as dangerous before save, placed in the dedicated warning section, and they are off by default unless the user enables them intentionally.

## Model discovery and fallback

The model field is always editable. Catalog entries represent a snapshot of models that were discoverable on the maintainer machine when the catalog was generated; they are suggestions, not authorization or entitlement guarantees.

- `agy`: model suggestions come from `agy models` in the maintainers' snapshot
- Codex: model suggestions come from the app-server `model/list` path when the dev snapshot exposes it
- Claude Code and Copilot: the catalog records the manual or interactive model guidance and leaves the field editable for manual names

When a model suggestion is stale or unavailable, ithyno keeps the structured fields visible and does not mark the adapter as unsupported. The model field stays editable, and the user can type a model name or reuse a previous value.

## Version dependence and compatibility

The JSON catalog is versioned in git and reviewed like any other shipped artifact. It keeps the dashboard deterministic while preserving CLI-version differences through maintainable snapshots rather than live inspection.

Examples:

- a CLI may add or remove flags between versions, so the generator snapshot is the source of truth for supported options in the shipped app
- Codex model metadata can include structured `supportedReasoningEfforts` entries, which the parser preserves rather than dropping them
- prompts, runtime flags, and dispatcher-generated values such as `-p`, `--resume`, `--continue`, and Codex `exec` remain outside the saved `args[]` payload and are handled by the runtime instead

## Advanced args fallback

Unsupported or custom argv remains available through the collapsible Advanced args editor. The field preserves every unknown argument and its original ordering so the user can keep project-specific or future flags without losing data.

The exact argv preview shown beneath the builder reflects the persisted command + `args[]` values that will be written to `agents.yaml`. This is the escape hatch that keeps the UI forward-compatible when a CLI adds new flags or when the user deliberately writes a custom option that ithyno does not yet model.
