# Agent CLI command builder

This UI uses a checked-in capability catalog rather than probing the user's environment at runtime. The catalog is generated by maintainers with an explicit opt-in script and is committed to the repo so the app remains safe and deterministic.

See the source research note at [docs/ideas/2026-10-06-agent-cli-command-builder-research.md](../ideas/2026-10-06-agent-cli-command-builder-research.md) for the original discovery notes and version-dependent caveats.

## Why the runtime does not inspect local CLIs

The architecture explicitly forbids runtime execution or inspection of user-installed Claude Code, Codex, Antigravity, or GitHub Copilot CLIs. The application does not resolve executable paths, spawn `app-server`, or call model-list commands while the dashboard is open. This avoids user-environment scanning and prevents arbitrary subprocess execution from the UI or server runtime.

Instead, the project ships a generated file at `server/agent-cli-capabilities.json`. The runtime reads that static catalog and treats it as the system-of-record for supported fields and model suggestions.

## Maintainer workflow

Maintainers regenerate the catalog intentionally:

```bash
npm run generate:cli-catalog
```

The script is allow-listed and only probes the supported CLIs when the maintainer explicitly runs it. The checked-in JSON is then reviewed and shipped with the app.

### Where the CLI arguments and models come from

The generator does not scrape arbitrary commands from an end user's machine. Its inputs are deliberately split by responsibility:

- Supported argument names, kinds, choices, categories, aliases, and dangerous flags are maintained in `server/agents/cli-command-builder.ts`.
- Claude Code model suggestions are maintained from Anthropic's official model-alias reference.
- GitHub Copilot CLI model suggestions are maintained from GitHub's official supported-model reference.
- Codex model suggestions are captured from the allow-listed `codex app-server` `model/list` request when a maintainer regenerates the catalog.
- Antigravity model suggestions are captured from the allow-listed `agy models` command when a maintainer regenerates the catalog.
- Installed CLI versions are recorded as snapshot metadata. They do not cause the shipped application to probe an end user's CLI.

After changing an adapter or refreshing model data, run the generator and review the resulting JSON diff:

```bash
npm run generate:cli-catalog
git diff -- server/agent-cli-capabilities.json
```

Do not accept a generated model list as an availability guarantee. Account permissions, organization policy, gateways, and later CLI releases can change which models a user can actually run.

### Testing generated arguments against installed CLIs

The deterministic parser and UI tests use fixtures and run as part of the normal test suite. A separate maintainer smoke test can validate the generated argument combinations against the real CLIs installed on the development machine:

```bash
npm run test:cli-argv
```

This command:

1. Finds the supported installed CLIs (`claude`, `codex`, `agy`, and `copilot`).
2. Builds adapter-specific argument combinations from the checked-in catalog.
3. Starts each CLI with those arguments but sends no prompt or model input.
4. Treats an immediate argument-parser rejection as a failure.
5. Stops a CLI after a short grace period if it accepted the arguments and remained running.

Because no prompt is submitted, the smoke test does not request model inference or consume inference tokens. A CLI may still perform its normal local startup, authentication check, or session lookup before it exits or is stopped.

Missing CLIs are reported as skipped by default. For a release-maintainer machine that is expected to have every supported CLI installed, use:

```bash
npm run test:cli-argv:all
```

The real-CLI smoke test is intentionally not run in GitHub Actions because hosted runners do not contain authenticated installations of every supported CLI. CI runs `scripts/verify-agent-cli-argv.test.mjs` instead; that fixture test checks adapter isolation, dangerous-flag separation, and parser-error classification without starting external CLIs.

The smoke test proves that the installed CLI parser accepts the generated flags and their placement. It does not prove model entitlement, authentication, successful inference, or compatibility with every historical and future CLI version.

## Supported field behavior

The builder renders the fields defined in the bundled catalog. These are grouped in a deterministic order that matches the runtime contract:

1. Model (`--model`, `--profile`, `--auto-tier`)
2. Reasoning (`--effort`, `--reasoning-effort`)
3. Permissions (`--permission-mode`, `--ask-for-approval`, `--approve-for-me`)
4. Sandbox (`--sandbox`)
5. Execution (`--mode`, `--autopilot`, `--plan`)
6. Context (`--context`, `--add-dir`)
7. Tools & Access (`--allow-tool`, `--deny-tool`, `--allow-url`, and equivalent adapter-defined access controls)
8. Unattended / Dangerous (warning-colored, explicit opt-in only)

Arguments not represented by these groups remain editable in the separate Free-form args field.

- Claude Code: `--model`, `--effort`, `--permission-mode`, `--dangerously-skip-permissions`
- Codex: `--model`, `--profile`, `--sandbox`, `--ask-for-approval`, `--approve-for-me`, `--dangerously-bypass-approvals-and-sandbox`
- Antigravity (`agy`): `--model`, `--effort`, `--mode`, `--sandbox`, `--dangerously-skip-permissions`
- GitHub Copilot CLI: `--model`, `--reasoning-effort`, `--context`, `--auto-tier`, `--mode`, `--allow-all`, `--yolo`

Dangerous controls remain visible but are labeled as dangerous before save, placed in the dedicated warning section, and they are off by default unless the user enables them intentionally.

## Model discovery and fallback

The model field is always editable. Catalog entries represent a snapshot of models that were discoverable on the maintainer machine when the catalog was generated; they are suggestions, not authorization or entitlement guarantees.

- `agy`: model suggestions come from `agy models` in the maintainers' snapshot
- Codex: model suggestions come from the app-server `model/list` path when the dev snapshot exposes it
- Claude Code: model suggestions come from Anthropic's official [Claude Code model configuration reference](https://code.claude.com/docs/en/model-config#model-aliases), including the portable aliases; provider-specific and gateway names remain editable
- GitHub Copilot CLI: model suggestions are copied into the reviewed catalog from GitHub's official [Copilot CLI supported-models reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference#supported-models); the field remains editable because plan and organization policy affect availability

When a model suggestion is stale or unavailable, ithyno keeps the structured fields visible and does not mark the adapter as unsupported. The model field stays editable, and the user can type a model name or reuse a previous value.

## Version dependence and compatibility

The JSON catalog is versioned in git and reviewed like any other shipped artifact. It keeps the dashboard deterministic while preserving CLI-version differences through maintainable snapshots rather than live inspection.

Examples:

- a CLI may add or remove flags between versions, so the generator snapshot is the source of truth for supported options in the shipped app
- Codex model metadata can include structured `supportedReasoningEfforts` entries, which the parser preserves rather than dropping them
- worker prompts and dispatcher-generated values such as `-p`, change IDs, artifact contracts, and Codex `exec` remain outside the saved `args[]` payload; Manager session choices are tracked by `sessionStartup` and their CLI-specific resume flags are resolved at PTY startup

## Free-form args

Unsupported or custom argv remains editable through the separate Free-form args field. It preserves unknown arguments so the user can keep project-specific or future flags without losing data. The dialog does not show a separate Advanced preview; the editable structured controls and Free-form args are the source of the saved `command` and `args[]` values.

## Manager session startup

Session startup is shown only when editing a Manager and the selected CLI supports it. For Claude Code, **Managed project session ID** is the default for newly declared Managers. The policy is stored separately from normal CLI arguments:

```yaml
agents:
  - name: manager
    mode: live-shell
    roles: [manager]
    command: claude
    sessionStartup: managed
    args: [--model, sonnet]
```

On the first launch, ithyno creates a project-local UUID in `.ithyno/session-claude` and starts Claude with `--session-id <UUID>`. On later launches it uses `--resume <UUID>`. Options such as `--model` remain active in both cases.

The other choices have different semantics:

- **Start a new session** starts the CLI without a resume target.
- **Choose a session to resume** uses the CLI's session picker.
- **Continue the latest session** uses the CLI's latest-session behavior.
- A manually entered `--resume <id>` or Claude `--session-id <id>` is shown as a custom session target.

For an Agy Manager, the dialog provides **Start a new session**, **Continue the latest session**, and **Resume by conversation ID**. The last option shows a dedicated Conversation ID field and saves it as `--conversation <id>`; `--continue` remains an explicit choice because it can fail when no prior conversation exists.

Older `agents.yaml` files without `sessionStartup` keep their existing behavior. For backward compatibility, a Claude Manager with no arguments still uses ithyno's managed project session strategy; a Manager with explicit arguments continues to use those arguments exactly until it is saved through the updated UI.
